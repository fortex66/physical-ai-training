# 강화학습 개념 — 환경·Policy·Critic·보상·종료

**강화학습은 행동의 결과를 경험하고, 앞으로 얻을 누적 보상이 커지도록 행동 선택 방식을 개선하는 과정이다.**

## 1. Cartpole로 이해하기

카트 위의 막대를 세워두는 작업을 생각해 보자.
막대가 오른쪽으로 기울 때 카트를 적절히 움직이면 균형을 유지할 수 있다.
하지만 기울어진 각도만 같아도 막대가 넘어지는 중인지 돌아오는 중인지에 따라 필요한 행동은 달라진다.
그래서 각도뿐 아니라 속도도 관측에 넣는다.

| 용어 | 쉬운 의미 | Cartpole 예시 |
|---|---|---|
| 환경 · Environment | 행동하고 결과를 확인하는 세계 | 카트·막대와 물리 시뮬레이션 |
| 관측 · Observation | 행동 결정에 제공하는 정보 | 위치·각도·속도 |
| 행동 · Action | 환경에 적용할 명령 | 카트에 가할 힘 |
| 보상 · Reward | 정의한 기준에 따른 점수 | 직립 유지에 유리한 점수 |
| 정책 · Policy | 관측을 보고 행동을 선택하는 방법 | 현재 상태에 맞는 힘 선택 |
| 에피소드 · Episode | 시작부터 종료까지 한 번의 시도 | 초기화된 카트가 제한 시간 또는 실패까지 진행 |
| 학습 | 경험을 이용해 정책 개선 | 균형 유지에 유리한 힘을 더 잘 선택 |

관측은 환경의 전체 상태와 같지 않을 수 있다.
실제 로봇에서는 센서로 얻을 수 있는 정보, 시뮬레이션에서는 제공하기로 선택한 정보가 관측이다.

## 2. Policy와 Actor

**Policy는 ‘이 관측에서 어떤 행동을 선택할까?’에 대한 규칙이다.**
정책은 무작위 규칙이나 사람이 만든 제어 규칙으로도 표현할 수 있다.
신경망 정책은 관측을 입력하고 행동 또는 행동의 확률분포를 출력하도록 구현한다.

Actor-Critic 방식의 **Actor는 정책을 표현하는 신경망**이다.
학습 중에는 행동 분포에서 샘플을 뽑아 탐색하고, 경험에 따라 분포를 바꿀 수 있다.
학습 후 평가에서는 구현에 따라 분포의 평균 등 결정적인 행동을 사용할 수 있다.

20번의 `torch.randn()`은 관측과 무관하게 행동을 뽑는 랜덤 정책이다.
정책이라는 넓은 의미에는 해당하지만 신경망 정책을 학습하는 것은 아니다.

### `policy` 관측 그룹과 신경망은 다르다

```python
obs["policy"]
```

이는 정책에 제공할 관측을 담은 딕셔너리 항목이다.
`PolicyCfg(ObsGroup)`는 그 관측의 구성 설정이며 신경망을 정의한 클래스가 아니다.
관측 그룹 이름만으로 PPO가 자동 실행되지 않는다. 학습 라이브러리·래퍼·설정이 그 입력을 받아 정책에 연결한다.

## 3. Critic은 무엇을 하는가?

**Critic은 ‘현재 정책으로 이 상태에서 계속 행동하면 앞으로 어느 정도 보상을 얻을까?’를 추정한다.**
Actor가 행동을 선택한다면 Critic은 그 행동을 학습할 때 비교할 기대치를 제공한다.
Critic 자체도 경험으로 학습하는 신경망이며, 정답을 알고 있는 심판은 아니다.

예를 들어 현재 상태에서 앞으로 얻을 점수를 10점으로 예상했다고 하자.
설명용으로 경험 결과를 14점으로 추정했다면 예상보다 좋았고,
6점이라면 예상보다 좋지 않았던 것으로 해석할 수 있다.
이런 ‘예상 대비 얼마나 좋았나’를 **Advantage**라고 한다.
실제 PPO에서는 할인과 여러 step의 보상·가치 추정을 이용해 계산한다.

Critic은 정책 업데이트의 비교 기준을 만들어 학습의 변동을 줄이고 효율을 높이는 데 도움을 줄 수 있다.
하지만 항상 정확한 것도, 모든 강화학습 방법에서 같은 형태로 필수인 것도 아니다.
보상 함수를 대신 만들거나 로봇에 직접 행동 명령을 내리는 역할도 아니다.

### `critic` 관측 그룹은 선택 사항

학습 코드에서 Critic이 존재하는 것과 환경에 별도 `critic` 관측 그룹이 있는 것은 다르다.
Actor와 Critic은 같은 관측을 사용할 수도 있다.
별도 그룹을 정의하면 Critic에 추가 정보를 줄 수도 있으며, 입력 연결 방식은 학습 라이브러리·버전에 따라 확인해야 한다.

**Asymmetric Actor-Critic**은 예를 들어 다음처럼 구성한다.

| 입력 대상 | 제공하는 정보 |
|---|---|
| Actor | 실제 배포 시 얻을 수 있는 센서 관측 |
| Critic | 학습 중에만 사용할 시뮬레이션 내부의 추가 상태 |

Critic이 추가 상태로 가치 추정을 돕더라도, Actor가 배포에 필요한 입력을 확보해야 한다.
20번 제공 코드에는 별도 Critic 신경망도 `critic` 관측 그룹도 없다.

## 4. PPO·신경망·가중치와 라이브러리

PPO(Proximal Policy Optimization)는 경험을 이용해 정책을 개선하는 알고리즘이다.
한 번의 업데이트로 정책이 지나치게 바뀌는 것을 억제하는 목적을 갖는다.

| 구성 | 역할 |
|---|---|
| Isaac Sim | 물리·렌더링 시뮬레이션 |
| Isaac Lab | 로봇 학습 환경과 관측·행동·보상·종료 인터페이스 |
| RSL-RL | 이 튜토리얼에서 사용하는 별도 학습 라이브러리 · 신경망·PPO·학습 실행기 |
| 사용자 | 작업·환경·평가 기준과 학습 설정 선택 |

RSL-RL의 신경망은 PyTorch 코드로 구현돼 있다.
사용자는 은닉층·뉴런 수 등의 구조를 정하고, 라이브러리가 초기 가중치를 생성한다.
PPO가 경험을 수집해 가중치를 수정하고 결과를 체크포인트로 저장한다.
사용자가 가중치 숫자를 하나씩 정해서 넣는 방식은 아니다.

```text
환경·관측·행동·보상·종료 설정 + 신경망·학습 설정
                       ↓
관측 → Actor → 행동 → 환경 → 보상·다음 관측·종료 정보
        ↑                    ↓
        └── PPO + Critic으로 경험을 학습 ──┘
                       ↓
               가중치 체크포인트 저장
                       ↓
               로드한 정책으로 로봇 제어
```

은닉층 설정은 신경망의 구조를, 가중치는 학습한 동작을 나타낸다.
환경 수를 늘리는 것은 경험 수집을 병렬화하는 방법이며 신경망 자체를 더 크게 만드는 설정이 아니다.
PPO·Actor-Critic은 20번 이후의 학습을 이해하기 위한 설명이며, 20번에서 이미 실행 중인 기능은 아니다.

## 5. Termination과 Truncation

둘 다 현재 에피소드의 수집을 끝낼 수 있지만 **끝난 이유와 학습에서의 해석이 다르다.**

| 구분 | 의미 | 예시 |
|---|---|---|
| Termination | 정의한 작업 자체가 종결 상태에 도달 | 실패 조건, 성공 조건 |
| Truncation | 작업의 종결과 별개로 수집을 중단 | 외부 시간 상한 |

Termination은 실패만 뜻하지 않는다. 목표 달성을 종결로 설계하면 성공도 termination이다.
20번은 카트 경계 이탈을 termination으로, 5초 제한을 truncation으로 설정했다.
두 조건이 같은 step에 만족되면 두 플래그가 함께 참일 수도 있다.
작업 자체에 제한 시간이 포함된 유한 시간 문제라면 시간 종료를 어떻게 정의할지 별도로 설계해야 한다.

### Critic 학습에 왜 중요한가?

- **진짜 종결:** 그 에피소드에서 앞으로 이어지는 보상은 없다. 마지막 보상은 사용하되 종결 이후의 가치 기여를 0으로 본다.
- **단순 시간 중단:** 계속 진행할 수 있는 작업을 잘라 기록했으므로, 남은 가치를 Critic으로 추정해 보충할 수 있다.

이처럼 추정 가치를 이용해 학습 목표를 만드는 것을 **Bootstrapping**이라고 한다.
마지막 보상만으로 이후 가능성을 모두 0으로 처리하면 시간 제한 부근의 가치를 잘못 배울 수 있다.

두 플래그를 반환한다고 보정이 저절로 완성되는 것은 아니다.
학습기·래퍼가 종료 이유와 끝나기 직전 상태를 올바르게 처리해야 한다.
자동 리셋 환경에서 반환된 새 에피소드의 관측을 이전 에피소드의 마지막 상태로 잘못 사용하지 않도록 주의한다.

## 6. 보상 설계 — 무엇을 배우게 할까?

**정책은 사용자의 의도가 아니라 코드로 정의된 보상을 높이도록 학습한다.**
따라서 원하는 동작과 보상 기준이 맞는지 확인해야 한다.

| 목적 | 보상 설계 예시 | 함께 생각할 점 |
|---|---|---|
| 균형 유지 | 직립 편차에 감점 | 어느 각도부터 실패로 볼 것인가? |
| 오래 유지 | 진행 중 보상 | 나쁜 자세로 버티기만 해도 보상을 받는가? |
| 부드러운 동작 | 속도·행동 변화에 감점 | 균형 회복에 필요한 움직임까지 억제하지 않는가? |
| 목표 도달 | 도달 보상·거리 감소 신호 | 멈추거나 쉬운 조건만 이용하는 행동이 유리해지지 않는가? |
| 실패 방지 | 실패 감점·종료 | 감점 크기와 다른 항의 상대 크기가 적절한가? |

### 자주 구분할 개념

- **Dense reward:** 각도·거리처럼 자주 계산되는 학습 신호.
- **Sparse reward:** 성공했을 때만 주는 점수처럼 드문 신호.
- **Reward shaping:** 목표 행동을 배우기 쉽게 중간 평가 항을 더하는 것. 최적 행동을 바꿀 수 있으므로 의도와 맞는지 확인한다.
- **Reward hacking:** 정의한 점수는 잘 얻지만 실제 목적과 어긋난 행동을 하는 현상.

20번의 각도·속도 감점은 자주 계산되는 신호다.
막대가 기울었다고 종료되는 것은 아니므로 ‘막대를 세우기’와 ‘카트가 경계 안에 있기’ 조건을 혼동하면 안 된다.
행동·관측·보상·종료·초기화는 서로 연결해서 설계한다.

### 가중치·시간 간격·평가 지표

가중치만 비교하지 말고 각 항의 실제 값과 단위·규모도 함께 본다.
Isaac Lab v2.3.2 보상 매니저는 가중합에 환경 시간 간격을 곱한다.
따라서 반환 보상과 주석의 +1·-2가 숫자 그대로 같지 않을 수 있다.

정책 평가에서는 총 보상뿐 아니라 성공률, 유지 시간, 자세 오차, 힘·동작의 크기와 영상도 확인한다.
환경·시간 간격·보상 정의가 다르면 점수 크기를 바로 비교하기 어렵다.

## 7. 에피소드·step·iteration·병렬 환경

| 용어 | 뜻 |
|---|---|
| 물리 step | 물리 엔진을 한 번 진행 |
| 환경 step | 행동 적용 후 물리를 진행하고 관측·보상 반환 |
| 에피소드 | 시작부터 종료까지의 시도 |
| 학습 iteration | 경험 수집·모델 업데이트 단위 · 실행기 정의에 따름 |
| 병렬 환경 수 | 함께 실행해 경험을 수집하는 환경 개수 |

20번은 환경 step 한 번에 물리 step 두 번을 진행한다.
환경 4개를 100번 step하면 최대 400개의 전이를 만들지만, 서로 이어진 경험은 독립적인 시도 400개와 같지 않다.
학습 시간을 판단할 때 에피소드·step·업데이트 횟수를 서로 바꿔 읽지 않는다.

랜덤화 설정만 실행해도 정책이 학습되는 것은 아니며, 학습 실행기에 연결해야 한다.

## 9. 관측 설계 — 정보의 표현도 학습에 영향을 준다

정책에 필요한 정보인지, 센서로 얻을 수 있는지와 표현·단위·순서를 함께 확인한다.
관측을 늘린다고 반드시 더 잘 배우는 것은 아니다.
21번은 기존 상태를 sin·cos와 정규화 값으로 추가 표현한다.

| 처리 | 목적 | 주의할 점 |
|---|---|---|
| sin·cos 각도 표현 | ±π 경계의 주기성을 표현 | raw 각도도 남아 있으면 그 표현 역시 입력됨 |
| 정규화·scale | 값의 크기를 맞추기 | 모든 관측에 자동 적용되는 것은 아님 |
| clip | 범위를 제한 | 범위 밖 정보를 구분하지 못할 수 있음 |
| noise | 센서 오차 등의 변동을 모사 | 설정과 활성화 여부를 함께 확인 |

21번 관측은 4 → 7차원으로 바뀐다.
입력 크기·순서·전처리가 달라지면 기존 체크포인트의 입력 계약도 달라진다.
정보의 의미와 신경망 입력 형상을 함께 관리해야 한다.

## 10. 보상 항 해석 — 점수 이름보다 실제 함수를 확인한다

직립 보상 `cos(각도)`는 직립 +1, 수평 0, 거꾸로 -1로 평가한다.
음수도 가능한 함수이며 0~1 보너스와 다르다.
가우시안 중앙 보상은 중심에서 최대이며 sigma가 허용 위치 범위의 넓이를 조절한다.
‘energy’라는 이름을 붙여도 raw action 제곱합이면 실제 에너지 측정이 아닌 행동 크기 억제 항이다.

<p align="center">
  <img src="diagrams/05-reward-accounting.png" alt="보상 로그와 누적값의 관계" width="900">
</p>
<p align="center"><sub>그림 5. 보상 로그와 누적값의 관계</sub></p>

총점만 보면 어떤 항이 영향을 줬는지 알기 어렵다.
항별 값을 보되 원시 값, 가중 값, step 기여와 에피소드 누적을 구분한다.
Isaac Lab v2.3.2의 `_step_reward`는 이름과 달리 dt 적용 전 가중 값이며, 에피소드 누적 값도 아니다.

보상 변경 효과를 확인하려면 랜덤 데모뿐 아니라 정책 학습·평가를 같은 조건에서 비교해야 한다.
학습 보상 자체가 달라진 실험에서는 총점 크기만으로 우열을 판단하지 않는다.

## 11. 액션 공간 — 정책 출력을 로봇 명령으로 해석하기

정책은 숫자를 출력하지만 그 숫자가 무엇을 뜻하는지는 환경의 액션 설계가 정한다.
‘0.5만큼 행동한다’ 대신 ‘50 N으로 민다’, ‘1 m를 목표로 한다’, ‘2.5 m/s를 목표로 한다’처럼 해석해야 한다.

<p align="center">
  <img src="diagrams/10-action-space.png" alt="정책 출력에서 실제 구동까지" width="840">
</p>
<p align="center"><sub>그림 10. 정책 출력에서 실제 구동까지</sub></p>

| 단계 | 역할 | 이번 22장 예 |
|---|---|---|
| 정책 또는 테스트 입력 | 행동 값 선택 | 사인파·균등 난수 · 신경망 없음 |
| ActionTerm | 대상 관절·명령 종류·scale/offset 지정 | 카트 하나에 힘/위치/속도 명령 |
| actuator | 목표와 현재 상태로 구동 힘 결정 | 위치 stiffness·속도 damping·힘 제한 |
| 물리 엔진 | 힘과 중력·접촉으로 다음 상태 계산 | 두 물리 step 후 새 관측·보상 반환 |

위치·속도 제어는 로봇을 목표값으로 순간 이동시키지 않는다. 추종은 게인·질량·힘 제한 등에 달려 있다.
위치 제어를 선택해도 stiffness=0이면 위치 오차에 반응하지 않는다. 기본 Cartpole을 그대로 사용한 22번이 이 경우다.
힘 명령도 actuator의 감쇠와 함께 작용할 수 있으므로 ‘effort면 게인 무시’를 보편 법칙으로 해석하지 않는다.

`scale`은 값의 크기를 바꾸고 `offset`은 기준을 옮긴다. 둘 다 범위 제한 장치는 아니다.
입력 제한, 처리된 명령의 clip, actuator의 힘 제한, 관절 위치 제한을 구분한다.
회전 관절과 직선 관절은 동일한 ActionCfg를 쓰더라도 명령 단위가 다르다.

**어떤 액션 방식이 좋은지는 작업과 실제 구동 인터페이스에 달려 있다.**
위치 명령을 받는 로봇에 정책을 배포하려면 학습 당시 위치 제어기의 응답도 맞춰야 한다.
관측·액션 차원이 같더라도 모드·scale·offset·관절 순서를 바꾸면 기존 가중치가 의도한 동작과 달라질 수 있다.
정책 체크포인트와 환경 설정을 함께 보관한다.

22번은 액션 인터페이스 테스트이고 PPO 학습이 아니다. 무작위 행동의 점수는 학습 성능과 구분한다.

23번은 Scene·Action·Observation·Reward·Termination·Event를 하나의 Cfg로 조립한다.

순수 시간 제한과 task 실패가 동시에 일어날 수도 있으므로 두 종료 플래그를 모두 기록한다.

Baseline은 학습 전 행동 규칙의 성능을 재어 이후 비교할 기준을 만드는 것이다.
23번의 랜덤 행동은 정규분포를 ±1로 clamp하며 22번 균등 난수와 다르다.
완료 에피소드만 평균 내면 아직 끝나지 않은 긴 에피소드가 빠지고 짧게 실패한 환경의 기록이 더 많이 포함될 수 있다.
같은 환경·초기화·seed·평가 예산에서 완결 에피소드의 보상, 유지 시간, 실패/timeout 수와 실제 작업 오차를 비교한다.

병렬 환경 100개 × 500 환경 step이면 50,000개 전이를 만들 수 있지만, 학습 실행기가 없으면 가중치는 갱신되지 않는다.
24번의 실제 연결은 7차원 관측과 1차원 행동을 가진 같은 핵심 환경 설계에 RSL-RL과 PPO 실행기를 붙이는 것이다.
정책 입력·행동 단위·보상·종료 규칙을 학습과 평가에서 맞춰야 점수 차이를 해석할 수 있다.

## 13. PPO 실제 학습 — 경험으로 Actor와 Critic을 바꾸기

24번부터는 Actor가 행동을 고르고 학습기가 가중치를 업데이트한다. 환경은 보상을 계산하고, PPO는 보상과 가치 추정으로 학습 신호를 만든다.
같은 관측 7개를 Actor·Critic에 넣되 Actor는 행동 분포, Critic은 미래 할인 누적 가치 하나를 출력한다.
두 네트워크는 각각 은닉층 `[32, 32]`이며 초기 가중치는 라이브러리가 생성한다.

<p align="center">
  <img src="diagrams/12-lesson24-training.png" alt="실제 Cartpole 학습 반복" width="337">
</p>
<p align="center"><sub>그림 12. 실제 Cartpole 학습 반복</sub></p>

### Rollout과 학습의 시간은 나눠 생각한다

현재 정책으로 1024환경에서 16 step씩 경험을 수집한다. 각 전이는 관측·행동·보상·종료와 정책/가치 정보를 가진다.
한 번 수집한 16,384개 전이로 여러 optimizer step을 수행하고, 바뀐 정책으로 다음 경험을 모은다.
16 step의 수집 구간은 300 step 에피소드와 다르다. 에피소드가 끝나기 전에 Critic으로 이후 가치를 추정해 학습할 수 있다.

| 단위 | 이번 설정 |
|---|---|
| 환경 step | 물리 step 2회 · 1/60초 |
| rollout | 환경당 16 step · 총 16,384 전이 |
| mini-batch | 4096개 전이 |
| epoch | 같은 rollout을 5회 사용 |
| iteration | rollout 수집 + 목표 계산 + 학습 + 기록 |
| 150 iteration | 2,457,600개 새 전이 · 기본 optimizer 3000회 |

PPO가 on-policy라는 것은 현재 정책으로 모은 경험을 주로 사용한다는 뜻이다. 같은 rollout을 몇 epoch 사용하는 것과 오래된 replay buffer를 계속 사용하는 것은 구분한다.

### Advantage는 즉시 보상만 보고 판단하지 않는다

보상은 지금 받은 점수, value는 앞으로의 할인 누적 보상 예측, return target은 보상과 bootstrap으로 만든 학습 목표다.
Advantage는 ‘이 행동이 현재 정책의 예상보다 얼마나 유리했나’를 나타낸다.
GAE는 `지금 보상 + 할인한 다음 가치 - 지금 가치`라는 TD 오차들을 여러 step에 걸쳐 섞는다. gamma는 미래 할인, lambda는 여러 길이의 추정 간 균형을 조절한다.
따라서 `즉시 보상 - Critic 값`만으로 설명하면 미래 보상과 시간 단위가 빠진다.

<p align="center">
  <img src="diagrams/13-ppo-update.png" alt="Advantage와 두 손실이 가중치를 바꾸는 과정" width="900">
</p>
<p align="center"><sub>그림 13. Advantage와 두 손실이 가중치를 바꾸는 과정</sub></p>

Actor는 양의 Advantage 행동을 더 자주, 음의 Advantage 행동을 덜 자주 고르도록 목적을 구성한다. Critic은 return target을 더 잘 예측하도록 학습한다.
이때 신경망 역전파가 수정 방향을 계산하고 optimizer가 가중치를 바꾼다.

### PPO clip·탐색·학습률은 서로 다른 기능이다

PPO는 같은 행동의 새/이전 정책 확률비로 정책 개선 목적을 만들고, clip된 목적과 비교해 지나친 개선을 억제하려 한다.
clip=0.2는 확률비 목적의 0.8~1.2 범위에 사용하며, 행동 ±0.2나 가중치 변화 ±20% 제한을 뜻하지 않는다. 모든 정책 변화를 강제로 막는 보장도 아니다.

탐색 σ는 행동 분포의 퍼짐이다. 처음 1.0으로 시작하고 학습된다. entropy 보너스는 정책이 너무 빨리 한 행동에 집중하지 않도록 장려한다.
연속 분포 entropy는 음수일 수 있다. 탐색이 줄었다는 사실만으로 성공을 판단하지 않는다.
학습률은 한 번 수정할 크기, gradient clipping은 수정 방향의 gradient 크기 제한, KL 기준은 이전/새 분포 변화에 따라 학습률을 조정하는 기준이다.

### 체크포인트·학습 로그·평가는 다르다

체크포인트에는 정책·가치·탐색 가중치와 optimizer·iteration 등 상태를 저장한다. model_0은 이번 Runner에서 첫 학습 iteration 후 모델이며 초기 가중치와 다르다.
실제 행동 실행에는 보통 Actor를 사용하지만 학습 재개에는 optimizer 등의 상태도 유용하다. 환경·관측 순서·행동 scale·라이브러리 버전도 함께 보관한다.

학습 중 mean_reward와 mean_episode_length는 최근 완료 에피소드의 평균이며 독립 평가 성공률이 아니다.
`Episode_Reward/*`는 이번 Isaac Lab에서 항별 누적을 최대 에피소드 시간으로 나눈 값이라 전체 점수와 구분한다.
최종 모델은 새 초기화·seed·평가 조건에서 보상·유지 시간·직립 오차·실패율을 다시 확인한다.

이번 실제 로그는 평균 보상 0.45→17.29, 길이 9.7→300 step으로 향상됐다. 세부 곡선·원본 로그·모델은 [24번 기록](../../24-train-cartpole/README.md)에 있다.

## 14. 학습·추론·평가 — 학습한 것은 경로가 아니라 정책이다

학습 중 PPO는 현재 정책의 분포에서 행동을 샘플링하고, 경험으로 정책 가중치를 바꾼다. 처음부터 끝까지 관측과 무관한 완전 랜덤 탐색을 하는 것은 아니다.
추론은 저장된 정책이 현재 관측을 행동으로 바꾸는 계산이다. 성공한 과거 경로를 그대로 재생하는 것이 아니다.
평가는 고정한 정책의 추론을 여러 에피소드 실행하고 보상·유지 시간·실패 사유·작업 오차를 측정하는 절차다.

<p align="center">
  <img src="diagrams/14-lesson25-evaluation.png" alt="학습 정책과 랜덤 baseline을 분리해 평가" width="554">
</p>
<p align="center"><sub>그림 14. 학습 정책과 랜덤 baseline을 분리해 평가</sub></p>

이번 `get_inference_policy()`는 Actor 평균 μ를 사용해 탐색 샘플링을 제거한다.
`torch.no_grad()`는 gradient 기록을 끄며, 그것 자체가 deterministic 행동을 만드는 것은 아니다. 모델 eval 모드와 가중치 업데이트 여부도 각각 구분한다.
확률적 정책을 배포하려면 그 샘플링 방식도 평가할 수 있으며 모든 추론이 deterministic이어야 하는 것은 아니다.

### 최신 모델과 최선 모델은 다르다

자동 탐색은 후보 폴더에서 iteration 숫자가 큰 체크포인트를 찾을 뿐 성능을 비교하지 않는다.
선택용 평가로 모델을 비교하고 최종 보고는 별도 초기 상태·seed에서 확인한다.
모델 구조뿐 아니라 관측 순서·단위·정규화·액션 scale도 학습 때의 계약과 맞춰야 한다.

### 성공률은 정의와 분모를 함께 읽는다

25번의 성공률은 실제로 **길이 ≥290 step** 비율이다. 환경 dt=1/60초에서 약 4.83초이므로 실패 없이 5초 전체를 채웠다는 판정과 다르다.
엄밀한 balancing 성공은 task 실패 없이 timeout 도달 여부와 직립·중앙 오차 등을 함께 정해 측정한다.
최대·최소는 범위이며 분산·표준편차는 별도로 계산해야 한다.

제공 영상의 학습 정책은 64회·평균 보상 17.28·길이 300, 랜덤은 65회·평균 보상 1.61·길이 34.7이었다.
랜덤의 65회는 동시 완료를 모두 추가한 결과이며 목표 64회와 구분한다. 코드는 실제 완료 수를 분모로 사용한다.
같은 seed·초기 상태·표본 수·종료 규칙과 배포 행동 모드를 기록해 비교하고, 이 결과를 모든 조건의 성공률로 일반화하지 않는다.

## 16. obs·action·rew·종료 신호의 피드백 루프

맞다. **관측으로 행동을 정하고 환경을 한 step 진행한 뒤, 반환된 새 관측으로 다음 행동을 정하는 과정이 반복된다.**
동시에 보상·종료 정보는 학습 경험과 에피소드 관리에 전달된다. 모든 반환값이 Actor 입력으로 그대로 들어가는 것은 아니다.

<p align="center">
  <img src="diagrams/16-step-feedback.png" alt="관측·행동·보상·종료 신호의 시간 전개 구조" width="490">
</p>
<p align="center"><sub>그림 16. 관측·행동·보상·종료 신호의 시간 전개 구조</sub></p>

그림은 같은 루프의 현재 step과 다음 정책 호출을 시간 순서대로 펼쳤다. θ는 정책 가중치다. r(t)는 action(t)로 만든 전이의 보상을 뜻한다.
`info`는 그림에서 생략한 부가 정보 딕셔너리이며 timeout 정보·로그 등이 들어갈 수 있다. 경험 버퍼에는 그림에 표시한 보상·종료 정보 외에 관측·행동·가치·행동 확률 정보도 함께 저장한다.

### 반환값의 역할을 나눠 읽기

| 값 | 이번 step에서의 의미 | 다음에 쓰이는 곳 |
|---|---|---|
| `obs` | 행동을 고르기 전 현재 관측 | Actor 입력 · 학습 시 Critic 입력 |
| `action` | 정책 또는 테스트 규칙이 고른 명령 | ActionManager → actuator → 물리 진행 |
| `next_obs` | step 후 반환한 관측 | 다음 Actor 호출 · 가치 추정/학습의 상태 정보 |
| `rew` | 이번 전이에 대한 환경 점수 | 누적 평가 점수 · return/Advantage 계산 |
| `terminated` | 태스크 정의상 종료 상태 도달 | 에피소드 구분 · 가치 연결 처리 |
| `truncated` | 시간 제한 등 외부 기준으로 중단 | 에피소드 구분 · timeout bootstrap 처리 |
| `info` | 보조 정보 | 종료 원인·로그·wrapper의 timeout 정보 등 |

**제어 피드백**은 `obs → policy → action → 물리 → next_obs`다.
**학습 피드백**은 여러 step의 경험과 보상·가치·종료 정보 → PPO 업데이트 → 바뀐 θ로 다음 rollout을 수집하는 경로다.
PPO는 보통 reward 하나를 받자마자 가중치를 한 번 바꾸지 않는다. 24번은 환경당 16 step을 모은 뒤 여러 mini-batch 업데이트를 한다.

### 한 step을 시간 순서대로 보기

1. 정책은 현재 `obs(t)`에서 `action(t)`를 계산한다.
2. Isaac Lab은 명령을 변환하고, 24번 설정에서는 같은 행동으로 물리 step 두 번을 진행한다.
3. 환경은 새 상태에서 종료 조건과 보상을 계산한다.
4. 완료한 환경만 자동 리셋하고 새 입력 관측을 반환한다.
5. 실행기는 점수·완료 정보를 기록하고, 반환 관측으로 다음 행동을 계산한다.

```python
# ManagerBasedRLEnv의 제어 흐름 설명용 · PPO 전체 구현은 아님
obs, info = env.reset()
while running:
    action = policy(obs)
    next_obs, rew, terminated, truncated, info = env.step(action)
    done = terminated | truncated
    # 평가: rew를 누적하고 done인 환경의 결과 기록
    # 학습: 현재 obs·행동·보상·가치·종료 정보를 rollout에 저장
    obs = next_obs
    # PPO는 정해진 rollout을 모은 뒤 별도 단계에서 가중치 업데이트
```

`env.step()` 호출마다 물리 상태는 바뀌지만 정책 가중치가 매번 바뀌는 것은 아니다.
또한 PPO의 역전파는 정책/가치 신경망의 손실에 적용하며 PhysX의 모든 물리 step을 통째로 미분해 경로를 찾는 방식이 아니다.

### 자동 리셋에서 특히 주의할 점

일반적인 단일 Gymnasium 환경은 완료 후 호출자가 reset해야 할 수 있다. 여기서는 Isaac Lab의 병렬 환경 내부에서 완료 환경만 자동 리셋한다.
따라서 완료 step의 `rew`·종료 플래그는 **끝난 에피소드** 결과이고 `next_obs`는 **새 에피소드 초기 관측**일 수 있다.
그 관측을 무조건 ‘실패 직전 상태’로 저장해 terminal value를 계산하면 잘못된 학습 목표를 만들 수 있다. timeout 처리는 wrapper·학습기 버전의 구현을 확인한다.

`done = terminated | truncated`는 둘 중 하나라도 발생하면 해당 에피소드가 끝났다는 뜻이다. task 종료와 시간 제한은 동시에 참일 수도 있다.
태스크 종료는 일반적으로 미래 가치 연결을 끊고, 순수 외부 시간 제한은 필요한 가치 bootstrap을 구분한다. 이번 RSL-RL 구현의 구체적 보정은 [24번 리뷰](../../24-train-cartpole/code-review.md#6-timeout-처리와-시작-카운터)에 정리했다.

평가·추론에서도 관측-행동 루프는 똑같이 반복되지만 보상은 성능 집계에 쓰고 θ는 고정한다. 20~23의 랜덤 데모는 새 관측을 받더라도 행동 생성에 사용하지 않는다는 차이가 있다.
