# 36번 기준 코드 리뷰

검토 대상은 [출처 manifest](analysis/source-manifest.json)의 PinkWink 기준 commit `14f85fc6edece7cbb1faa50aa9fe3adef205e87a` Python 7개다. 사용자 ZIP은 32MiB 전송 제한으로 열지 못해 수정 사항·모델·모션·event 로그를 검증하지 못했다.
강의 v2 PDF와 사용자 영상·사진을 기준 코드와 대조했다. Isaac Sim 실행·재학습은 하지 않았다.

## 1. 모션 모방이지만 PPO 강화학습이다

레퍼런스 관절각은 관측·보상·RSI에 사용한다. 36_2는 `OnPolicyRunner.learn()`을 호출하며 행동 라벨을 회귀하는 Behavior Cloning loss는 없다.
레퍼런스를 바꿔 재생하거나 추론하는 것만으로 새 동작이 학습되지는 않는다.

## 2. G1의 37관절 중 23개를 선택한다

G1_MINIMAL_CFG는 적은 충돌 메시를 쓰는 자산이다. PDF 8쪽의 ‘손가락 없는 최소 자산’과 달리, 35번과 같은 자산에서 BODY_JOINT_EXPR로 23개를 고른다.
관측 103개는 자기 상태 78개와 레퍼런스 23개·phase 2개다. 관절 선택 순서와 pkl의 23관절 순서는 별도로 검토해야 한다.
레퍼런스는 `build_joint_map()`으로 이름을 인덱스에 매핑한다. `waist_yaw→torso`, `wrist_roll→elbow_roll` alias가 있어 기구적으로 근사한 대응도 포함된다.
손가락이 행동에서 제외되어도 기본 joint_vel·joint_limits 항의 대상까지 23개라고 가정하지 않는다.

## 3. scale·위상·재생 보간

행동 scale .25는 기본 자세 기준 크기 변환이다. 매 step 최대 .25rad 이동이나 ±1 hard clip을 보장하지 않는다.
정책은 50Hz로 행동하고 레퍼런스는 30fps다. `frame_idx()`는 floor로 프레임을 고른다. sin/cos 위상 표현이 연속적이어도 참조 자세는 프레임 단위로 선택된다.
36_1 ghost는 두 프레임의 관절·이동을 선형 보간하고 quaternion을 정규화해 재생한다. quaternion 보간은 전용 SLERP와 같지 않다.
기본 파일만 `[42:155]`를 트림하고 다른 파일은 전체를 modulo로 반복한다. 마지막 속도를 직전 값으로 대체해도 자세·속도·가속도의 주기 연결까지 보장하지는 않는다.

## 4. RSI와 episode 카운터

기본 reset은 프레임 f와 phase0를 맞추고 관절 위치·유한차분 속도·root 높이를 설정한다. root 자세는 기본값으로 유지하고 평면 속도의 크기를 월드 +x에 쓴다.
원래 root quaternion·수직/횡이동·각속도를 모두 복원하는 RSI가 아니므로 회전·후진·앉기 동작에는 정보 손실이 크다.
위상에 episode_length_buf가 직접 들어가므로 `init_at_random_ep_len=False`가 중요하다. 카운터만 임의로 바꾸면 실제 자세와 관측·보상의 목표가 어긋난다.
RSI의 위상 분산과 timeout 카운터의 독립적인 분산은 다르다. joint_tracking>0이라는 사실만으로 RSI의 모든 상태가 올바르다고 입증할 수도 없다.

## 5. 속도 추종에서 버린 방향

기본 `ref_speed=norm(delta root_xy)×fps`는 항상 0 이상이다. 보상은 이 크기를 몸 기준 `root_lin_vel_b[:,0]`와 비교한다.
직선 전진에 맞춘 설계이며 쿵푸의 후진·옆걸음·yaw 변화에 필요한 월드 속도 벡터와 다르다. 음수 vx를 요구하는 동작을 정확히 따라도 낮은 점수가 나올 수 있다.
목표 yaw 관측·보상은 없지만 각속도 관측은 있다. 따라서 ‘어떤 회전도 학습할 수 없다’고 단정하기보다 회전 목표·초기화의 정보가 충분하지 않다고 설명한다.

## 6. 마지막 실패에서 모델·모션 불일치 가능성

36_3은 `--motion_pkl`을 생략하면 기본 보행 클립을 고른다. 쿵푸로 학습한 103입력 모델도 이 환경에 shape 오류 없이 load될 수 있다.
36-6 영상의 참조 속도 1.07은 기본 보행 출력과 같다. 이 단서만으로 파일명을 확정할 수는 없지만 쿵푸 파일로 평가했음을 입증하는 정보도 아니다.
명령·MOTION.pkl_name·모션 해시·checkpoint 전체 경로와 해시·환경 버전을 함께 기록해야 한다.

36_2에는 기존 모델 load가 없다. 모션을 바꿔 같은 스크립트를 실행하는 것은 자동 fine-tuning이 아니라 새 학습이다.
보행/쿵푸 모두 `g1_walking_tutorial` 고정 경로에 저장하므로 모델이 섞이거나 덮어써질 수 있다. 자동 탐색은 먼저 찾은 경로의 가장 큰 iteration을 고를 뿐, 의도한 모션·최고 성능·최근 시각을 검증하지 않는다.

## 7. 강의의 네 충돌과 전용판의 변경

PDF 33쪽의 클립 최저 z .306m, 저높이 프레임 7.9%, 전후 속도 -.85~+.90m/s, yaw 약 100도·최대 247도/s는 **강의가 제시한 분석**이다. 이번 데이터로 재측정하지 않았다.
전용판은 참조 높이 편차 .3m 종료, 월드 xy 속도 벡터와 yaw 추종, yaw 오차·참조 속도 관측, 회전·속도를 포함한 RSI, 기울기·속도 패널티 완화를 적용한다.
기울기 종료 .8rad는 상속되어 유지된다. 패널티도 0으로 없애는 것이 아니라 줄인다. 실제 넘어짐을 모두 허용하는 방식은 아니다.

관측 103→107로 입력층이 바뀌므로 같은 PPO·같은 hidden층이어도 기존 checkpoint와 완전 호환되지 않는다.
36_4는 별도 실험명 `g1_brucelee_tutorial`, episode 12초·기본 3000iteration으로 새 학습을 한다. 환경 수정만의 효과를 엄밀히 비교하려면 학습 예산·seed 등도 맞춰야 한다.
전용 RSI는 root quaternion·xyz 속도·yaw 각속도를 쓰지만 roll/pitch 각속도는 0이다. 모든 6D 운동을 완전히 복원하지는 않는다.
상속 함수들도 같은 확장 인스턴스를 사용하도록 `base.MOTION=MOTION`을 수행한다. 이름이 같은 객체가 자동으로 공유되는 것은 아니다.

## 8. 평가 통계의 한계

36_3은 같은 step의 모든 done 환경을 추가해 요청 10회를 넘어 12회까지 모을 수 있다. 성공률 조건은 `length>=475`이며 정확한 10초 timeout 비율과 다르다.
36_5도 600step의 95%인 570을 사용한다. wrapper의 `terminated=dones & ~truncated`는 동시 실패·시간 종료의 실패 정보를 지울 수 있다.
먼저 완료한 N개만 모으면 짧은 실패가 과대표집될 수 있다. 환경·위상·seed별로 고정 할당량을 완료하는 편이 더 공정하다.
RMS와 속도는 env.step 뒤에 읽으므로 종료 환경의 RSI reset 상태가 한 표본 섞인다. 짧은 실패에서 그 영향을 무조건 무시할 수 없다.
각 episode의 RMS를 계산한 뒤 산술평균한 값은 모든 전이를 합쳐 계산한 RMS와 다르다. 몸 기준 vx 평균도 미끄러짐·방향 정확도·작업 성공을 단독 판정하지 않는다.
특히 초기 속도를 RSI가 넣으므로 랜덤 정책도 짧은 시간에는 +0.96m/s를 보일 수 있다.

## 9. 재생·토크·원시 자료 구분

ghost는 `kinematic_enabled` 대신 dynamic 몸체에서 중력 off·PD 게인 0·상태 write를 사용한다. 중력 off가 실패해도 write를 계속하는 코드이므로 로그를 확인한다.
정책 로봇의 reset 뒤에도 ghost 시계는 계속 진행한다. 처음 같은 위상이었어도 계속 같은 프레임을 비교한다고 가정하지 않는다.
토크는 implicit PD 근사값이며 env0의 왼쪽 다리 6관절과 torso만 50Hz로 기록한다. 실측 센서·전체 200Hz 이력·소비 에너지와 다르다.
출력 PNG는 같은 파일명으로 덮어써질 수 있다. upstream PNG를 사용자 결과로 복사하지 않고 제공 영상에서 추출했다.
사진은 표시값만 전사했다. 원시 event가 없는 연속 학습 곡선, 쿵푸 학습 최종 수치, 전용판 성공률을 추정해 만들지 않았다.

## 10. 실제 모션과 LFS 포인터

사용자가 확인한 `version https://git-lfs.github.com/spec/v1`은 실제 모션이 아닌 LFS 포인터다. 첫 v에서 pickle이 실패하고 joblib에서도 문자 코드 118 오류가 날 수 있다.
데이터셋 Git 저장소에서 해당 파일을 LFS pull한 뒤 실제 크기 259443바이트와 필요시 포인터의 SHA256을 대조한다.
`--motion_list`는 파일명만 나열하므로 목록에 보여도 내용이 정상이라는 검증은 아니다. joblib 재시도도 포인터를 실제 모션으로 바꿔주지 않는다.
